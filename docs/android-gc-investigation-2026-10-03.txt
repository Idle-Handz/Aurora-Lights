Android content refresh: likely trigger and local mitigation
2026-10-03

Conclusion
The strongest explanation for the captured refresh crashes is a Mono garbage-
collector defect exposed by the larger allocation workload of the shared content
pipeline. Disabling concurrent collection allowed the previously failing v0.9.3
scenario to finish. This is an Android runtime mitigation, not a reduction in
content correctness checks or a rollback of the library.

Likely responsible application change
v0.8.4 used AuroraContentImporter.Import -> AuroraXmlCatalogReader.BuildCatalog
-> AuroraSqliteImporter.Import. It already imported in process on Android.
Commit b0cb4c1f0ea69d6e3f4075c78d13038ceaf46a01 (September 19) connected the app
to ContentImport.ImportAsync through the new Aurora.DataIntegration project.
That path runs LocalCorrectionSync and ContentPreparation, then the catalog
builder and writer, then candidate validation/provenance and atomic activation.
Later library updates extend that pipeline further.

ContentPreparation.FinalizeDeclarations holds file XML documents and declaration
records while resolving definitions and appends; finalized/provenance XML remains
available during import. The live application catalog is also retained so a
failed refresh can preserve working content. The prepared reader was introduced
separately in 394b2da, and can add allocation pressure during startup/reload.
This is a workload/lifetime change, not an inherent problem with NuGet packaging.

The interval has not been fully bisected. b0cb4c1 is the likely integration point,
not a proven first-bad commit. No standalone Settings or initial-load crash was
reproduced in the original three-version comparison. The hypothesis does not
establish that every reported phone crash has the same cause.

Runtime evidence
- Original x64 v0.9.0 and v0.9.3 full refreshes died with SIGSEGV on a .NET TP
  Worker, with the same leading libmonosgen-2.0.so frame addresses. Android exit
  history recorded APP CRASH(NATIVE), status 11, rather than a low-memory kill.
- Mono BuildId: bfc1d82f1672c69aa866f11ccf1c730c7726fc74, local runtime 10.0.12.
- At the fault PC 0x2c3b04, twelve instruction bytes uniquely match push_object+4
  in the same installed runtime's libmonosgen-2.0.a. Another frame matches
  sgen_alloc_obj_nolock. This is machine-code matching against the companion
  archive, not complete DWARF symbolication: the symbol server did not supply
  this build's debug file. Other frames were not independently fully resolved.
- dotnet/runtime issue 123495 reports the same push_object/Tarjan bridge crash
  family and was consolidated into 123537. A runtime maintainer recommended
  testing MONO_GC_PARAMS=major=marksweep. Reports include ARM64 devices and
  allocation-heavy XML work, but those reports alone do not prove our cause.
  https://github.com/dotnet/runtime/issues/123495
  https://github.com/dotnet/runtime/issues/123537
- Extracting libxamarin-app.so from both the original x64 APK and the published
  v0.9.3 ARM64 APK found major=marksweep-conc. The experimental APK contains only
  major=marksweep for that setting. See gc-fix/apk-settings.json.

Local change
Aurora.App/Platforms/Android/gc.env sets MONO_GC_PARAMS=major=marksweep and is
included as AndroidEnvironment only for the Android target. The explicit file
was chosen because an initial trial using AndroidEnableSGenConcurrent=false
still left marksweep-conc in the generated package; that trial was discarded.
The actual packaged environment was verified, not just the MSBuild input.
ARM64 project evaluation also includes the new environment item.

This keeps Mono, the library version, XML inputs, correction/conflict policies,
database schema, and activation safeguards intact. Windows and macOS do not
include this environment file. Non-concurrent collection can increase pause
times; it does not cure the importer's large working set. No nursery-size tuning
or experimental CoreCLR migration is included in this fix.

Remaining work before release / longer-term solution
1. Verify a release-signed ARM64 build on the user's Samsung Galaxy S22 Ultra,
   with its actual Android/One UI version and content set. Exercise cold load,
   Settings, full/incremental refresh, cancellation, and restart. The device
   model makes the ARM64 runtime hypothesis relevant but does not prove it.
2. Reduce retained XML copies in the library: stage declaration/provenance XML
   in a temporary SQLite store indexed by ID, process XML file-by-file, and feed
   finalized records to the writer in bounded batches. Preserve cross-file
   conflict/correction decisions and candidate activation; do not simply bypass
   those checks or discard the working catalog at refresh start.
3. Measure catalog allocation/lifetimes during reload and keep expensive reads
   off Settings renders. Profile before changing rollback/lifetime semantics.
4. Add an installed Android Release emulator smoke test with a representative
   corpus. Require observed completion, restart, and absence of native exits;
   mobile browser viewport tests do not exercise this runtime.
5. Re-evaluate this temporary GC setting when an independently validated runtime
   update resolves the defect. A runtime migration is a larger compatibility and
   performance exercise, not an automatic dependency bump in this patch.

around private worker preparation. Directory/settings inputs are captured before
Task.Run. XML reads, parsing, appends, generated class features, generated items,
and item detail initialization operate on a private candidate. The prior catalog,
populated flag, aliases, and deferred spell state remain available until success.

after all entries are present. Alias changes are staged, proxy state is primed at
