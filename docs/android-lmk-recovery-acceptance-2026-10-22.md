# Android recovery after a real low-memory kill — October 22, 2026

**Passed on the connected Samsung SM-S366V, Android 16 / API 36, ARM64.** Android reclaimed Aurora's background process for low memory. A newly created process offered both synthetic unsaved drafts, and both opened as separate recovery copies with their latest pending names and original build values retained. No Aurora production change or rebuild was necessary.

Windows x64 and Android remain the stable targets. Windows ARM64 and macOS remain experimental; Web remains deferred. This is acceptance of the tested package and scenario on this phone, not final v1.0 publication approval or coverage of every Android device.

## Method and observed process loss

With autosave temporarily off, two local synthetic Human/Wizard characters were opened together. Their pending names became `Android Memory A LMKRecovery` and `Android Memory B LMKRecovery`. A was inactive and B active. Both saved originals were verified unchanged before pressure started.

The existing isolated ARM64 memory helper was installed afresh and its activity placed in front of Aurora. Its foreground service allocated random native memory in 16 MiB blocks and touched each page repeatedly. It retained its 2,560 MiB allocation ceiling, 512 MiB minimum available-memory reserve, thermal stop and 25-minute automatic timeout. The host controller imposed a shorter nine-minute limit and stopped the helper promptly after Aurora disappeared. No memory-factor override, process-priority modification, simulated trim signal or explicit Aurora kill was used during this trial.

Independent USB samples recorded both live process IDs, `/proc/meminfo` and kernel memory pressure. The trial recorded **41 samples**; process loss was observed approximately **151.5 seconds** after starting. The helper remained alive at Aurora's disappearance. Its highest observed allocation was **2,160 MiB**; sampled available memory reached **628.85 MiB**. Peak ten-second memory-pressure averages were **23.83% some / 19.81% full**. All sampled helper thermal statuses were **0**. The helper's broad `MemoryInfo.LowMemory` flag stayed false, so that flag was not used to infer whether Android had killed Aurora.

The matching Android exit record was captured before any relaunch or manual cleanup:

| Field | Observed value |
| --- | --- |
| Process | `com.auroralights.app` |
| PID | `12849` |
| Device timestamp | `2026-10-22 11:24:24.962` |
| Reason | **`3 (LOW_MEMORY)`** |
| Importance | `400` — background |

Android defines this exit reason as a process killed by its low-memory killer. The actual OS record distinguishes this result from the earlier manual background-kill checks and from the earlier trial that reclaimed only the helper. [Android ApplicationExitInfo reference](https://developer.android.com/reference/android/app/ApplicationExitInfo#REASON_LOW_MEMORY), [process lifecycle documentation](https://developer.android.com/guide/components/activities/process-lifecycle).

## Recovery verification

Stopping the foreground helper allowed Android to return to Aurora and automatically create a new process, **PID 16334**. Both pending names were offered in the recovery panel. The acceptance driver initially expected no process to exist before explicitly reopening Aurora; that guard was corrected to recognize the already recreated process. It did not kill the new process or alter its recovery records.

Both **Open recovery copy** actions completed. Each created a separate `.dnd5e` and valid session sidecar. The latest name was verified in both the actual editable Manage field and the recovered XML's display/input values. A structural comparison retained all **175 build elements** in each recovered copy, normalizing only the deliberate name change and selection runtime GUIDs regenerated by ordinary engine loading. The two source files remained byte-identical throughout.

The inactive A draft displayed the existing warning that a save/build operation had been in progress and its choices should be checked. Its recovered build also passed the structural comparison. This accepts the tested cached-build fallback; it does not promise that an operation interrupted while changing choices can always be reconstructed beyond the last complete checkpoint.

Both recovery copies were closed cleanly without a save/discard prompt. Their original interrupted-session offers were consumed, with no remaining recovery offers. Autosave was restored to its original on setting.

## Cleanup and final verification

Only the two owned source fixtures, two recovery copies and their two session sidecars were removed. The temporary helper was uninstalled. Aurora's package version, first-install identity and data directory were unchanged.

The final complete comparison found **all 2,502 original external app files / 240,504,313 bytes byte-identical**, with **zero missing, changed or added files**. A clean cold start retained the usual connected account, original empty local library, no recovery offers and **18,458 compendium results**. Autosave was restored; network and rotation settings matched baseline. Aurora was left stopped on the phone's home screen. This byte comparison covers external app files; private preferences and secure storage were retained, with account and relevant setting behavior checked through the app.

Manual background termination used for the final clean-start/file-comparison checks occurs after the real low-memory exit and successful recovery. Those later cleanup exit records are not counted as low-memory evidence.

## Release implication and remaining limits

This closes the previously unobserved **recovery after Android's actual low-memory kill of Aurora** for two pending text drafts, including an inactive tab, on this API 36 Samsung and the exact storage2 package. Together with the [sustained-pressure pass](android-low-memory-acceptance-2026-10-22.md), it provides both survival/resume evidence and actual process-reclamation recovery evidence.

Lower-RAM devices, other Android versions/vendors, pressure during imports, exports, content activation or Drive operations, multi-hour leaks, abrupt power loss, and whole-filesystem exhaustion retain their separate limits. The final shipping artifact, signing/distribution and remaining release gates still require their own acceptance in the [readiness record](v1-release-readiness-2026-10-21.md). No commit, push, tag or release publication was performed.
