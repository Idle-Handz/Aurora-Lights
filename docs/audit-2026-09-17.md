# Audit — 2026-09-17

Full-codebase release-readiness review ahead of a minor version. Covers build
health, static reliability, security, and a re-verification of the Aurora.App
brittleness audit. Deliberately does not re-derive the existing content/import
audit trail (`pre-ui-validation-2026-09-15.md`, `content-database-rehearsal-2026-09-15.md`,
`content-priority-impact-audit-2026-09-13.md`, `remaining-conflict-table.md`) —
that work is already thorough and current; this review covers code-level ground
those docs don't.

## Headline

Code quality is solid: clean TODO/dead-code/disabled-test hygiene, 548/549 tests
pass, security review clean. The two findings most likely to affect a minor
release are a newly found build-pipeline flakiness, and the already-documented
Translator packaging gap (unchanged by this review, restated below for context).

## Build health

- All 12 non-MAUI projects (`Builder.Core`, `Builder.Data`, `Aurora.Logic`,
  `Aurora.Documents`, `Aurora.Importer`, `Aurora.PdfImport`, `Aurora.Presentation`,
  `Aurora.Components`, `Aurora.Web`, `Aurora.Lights`, `Aurora.Tests`,
  `Aurora.Presentation.Tests`) build clean, 0 errors, when built individually.
- 135 total warnings: `Aurora.Lights` (WPF) 110, `Builder.Data` 20, everything
  else 0. Categories worth a cleanup pass: `CS0618` obsolete API use (16;
  `StatisticAttributes.Cap/Type`, `GrantAttributes.Name`), `CA2200`
  rethrow-loses-stack (3; a real debuggability bug, not style), `CS4014`
  un-awaited async calls (10; fire-and-forget risk), `SYSLIB0051` obsolete
  serialization constructor (1).
- **New, since verified: cold solution builds of `Aurora Lights.sln` are flaky
  under default MSBuild parallelism.** Initial attempts produced three
  different failures: a file-lock race (`CS2012`), an Android resource error
  (`APT2260`, `reflections_splash not found`), and a missing ref-assembly on
  rebuild (`CS0006`). Follow-up testing isolated the cause: on a genuinely cold
  build, MSBuild's default project-level parallelism races on shared/overlapping
  output writes between unrelated projects (observed twice, with different
  victims each time — a locked Builder.Core/Aurora.Importer DLL, and separately
  a StaticWebAssets cache-file collision in Aurora.Components) which then
  cascades into `MSB4181` failures for every dependent project, including both
  of `Aurora.App`'s target frameworks. This is a parallel-build race in the
  solution graph generally, not specific to Aurora.App's MAUI multi-targeting.
  `/nodeReuse:false` does **not** fix it (still failed 1/2; node reuse only
  affects reuse *between* separate `dotnet build` invocations, not concurrency
  *within* one). `dotnet build "Aurora Lights.sln" -m:1` (single-node, no
  parallelism) fixed it deterministically, 2/2 clean cold builds at identical
  timing (~3:38 both times). Warm/incremental rebuilds were already clean 2/2
  with no flags — the flakiness is cold-build-only.
  **This does not affect the actual release pipeline**: `release.yml` and
  `build-windows.yml` never build the raw `.sln` — every job already restores
  and publishes `Aurora.App/Aurora.App.csproj` directly with an explicit
  `-f <TargetFramework>` per platform, which sidesteps this race entirely. The
  impact is limited to local dev-loop cold builds (`dotnet build` on the `.sln`,
  or an IDE "Build Solution" after a clean). Recommended workaround: build
  per-project (as CI already does) for normal dev, or pass `-m:1` when a full
  cold solution build is genuinely needed.

## Reliability — silent-failure sweep

The project's own `aurora-app-audit-checklist.md` names "silent no-op behavior"
as the biggest trust issue in the app. This review located the concrete
instances.

**Empty `catch {}` blocks: 49 across 24 files.** Worst clusters — fully empty,
no logging, no user feedback, all in interactive/data paths:

| File | Count | Impact |
| --- | ---: | --- |
| `Aurora.Web/Services/WebCharacterEngineService.cs` | 6 | Silently blanks fields on the Blazor character sheet (spell/slot/description population) |
| `Aurora.App/Services/BuildService.cs` | 6 | Around feature/spell-selection resolution during build |
| `Aurora.App/Services/CharacterSnapshot.cs` | 6 | DC/attack/prepared-spell/slot capture — see brittleness-audit item #9 below |
| `Aurora.App/Services/MauiCharacterSheetGenerator.cs` | 6 | Drops attack bonus, save DC, slots, or spell descriptions from the printable sheet with no trace |
| `Aurora.App/Services/EquipmentService.cs` | 2 | — |
| `Aurora.App/Services/ContentDatabaseService.cs` | 1 | Swallows failure when killing a process tree |
| `Aurora.App/Services/PdfPreviewService.cs` | 2 | — |

Aurora.Web's other services (`BaselineContentCatalogService`,
`PhaseZeroSessionCleanupService`/`WorkspaceService`, `WebCharacterSessionService`)
at least log via `_logger.LogWarning`/`LogDebug` — better, but still no
user-facing signal. These are mechanical, low-risk fixes now that they're
enumerated; recommended as the cheapest high-trust-payoff work item here.

**Update, same day: fixed.** All empty catches in the shared/priority surfaces
above — `BuildService.cs` (6), `CharacterSnapshot.cs` (6, including one not
originally counted: `IsAlwaysPreparedSpell`), `MauiCharacterSheetGenerator.cs`
(7, including its own separate `IsAlwaysPreparedSpell` copy), `EquipmentService.cs`
(2), `ContentService.cs` (1), `PdfPreviewPage.cs` (1), `PdfImportService.cs` (1),
`AppUpdateService.cs` (1), `WebCharacterEngineService.cs` (12, spread across
`BuildMagicSpellDetail`, `BuildMagicRuleSelectionGroups`, `GetDescription`,
`BuildMagicModel`, `ApplyPersistedMagicState`, `CollectSpellLevels`,
`CollectPreparedCasterSpellLevels`), `WebLogicBridgeServices.cs` (1),
`Aurora.Logic/Services/CharacterLoadCompatibilityService.cs` (1),
`AdvancementTimelineQuery.cs` (2), `BuildSelectionOptionResolver.cs` (3), and
`EquipmentItemDetailBuilder.cs` (2) — now log the exception with method-level
context via the existing idiom for each layer (`DebugLogService.Instance.LogException`
in Aurora.App, `Logger.Exception` in Aurora.Logic/Aurora.Web, both already
bridged to the in-app Console/persistent log). Behavior is unchanged (same
fallback values on failure); the difference is these failures are now
diagnosable instead of invisible.

Deliberately left as-is, with reasoning: best-effort temp-file cleanup
(`PdfPreviewPage.cs:250`, `CharacterContext.cs:161`, `CharacterFileIo.cs:100,156`),
killing an already-possibly-exited process on cancellation
(`ContentDatabaseService.cs:274`), closing an HTTP listener/response on shutdown
(`PdfPreviewService.cs:68,75`), a log sink's own write failure
(`FileLogger.cs`, `CompendiumSlider.xaml.cs:38` — logging a logging failure risks
recursion), and telemetry send failures (`AnalyticsEventHelper.cs`, the standard
"never let telemetry break the app" pattern). `LocalCorrectionSync.cs:183` got a
one-line comment for consistency with its two sibling catches rather than
logging, since it's already a documented "retry next sync" pattern.
Not addressed: empty catches confined to `Aurora.Lights` (WPF, legacy/decompiled,
deprioritized per `ROADMAP.md`) and to test files (intentional cleanup/expected-throw
patterns, not production code).
Verified: `Aurora.Logic`, `Aurora.Web`, and `Aurora.App` (net10.0-windows) all
build clean, 0 warnings/errors; `Aurora.Tests` still 548 passed/1 skipped/0 failed.

**Blocking-async anti-patterns** (deadlock/UI-hang risk):

- `Aurora.Logic/Services/ClassProgressionManager.cs:117` —
  `Task.Run(() => ...GenerateRandomHitPointsArray(...).Result).Wait();` double-blocks.
- `Aurora.Logic/Services/InventoryItemFactory.cs:271,389` —
  `GetOrStartSearchIndexBuild().GetAwaiter().GetResult()` blocks the calling
  thread while a search index builds on the thread pool.

**One real correctness bug**: `Aurora.App/Services/MauiSpellcastingSectionHandler.cs`
matches spellcasting profiles by `Name` (`.Where(p => !p.IsExtension && p.Name == spellcastingName)`,
~lines 26/52), and `GetPreparedIds` silently returns empty if two profiles
share a name. The code's own comment admits the cause: "Stable source ID +
profile name. Runtime GUIDs change when content reloads." A multiclass
character whose two classes/subclasses produce identically-named spellcasting
sections would see prepared spells vanish from display with no error. Cheap
fix: key the lookup off stable source ID instead of name.

Other findings (low priority, listed for completeness): `GenerateCharacterName()`
in `Aurora.Logic/CharacterManager.cs:1202` is `[Obsolete]` and unimplemented;
`Aurora.Logic/Services/Calculator/StatisticsHandler2.cs:339,351,356` logs a
known-bad calculation path and a "todoRules" fallback rather than fixing it, and
calls `Debugger.Break()` if a debugger is attached; two `NotSupportedException`
throws in active ViewModel logic (`SelectionRuleComboBoxViewModel.cs:512`,
`SelectionRuleExpanderViewModel.cs:767`) worth confirming are truly unreachable.
No dead code, no problematic disabled tests, and no hardcoded absolute paths
outside design-time-only code paths were found.

## Security review

Clean bill overall:

- **SQL injection**: none found. All value data uses parameterized commands;
  the only string-built SQL is for identifiers (table/column names) from
  hardcoded developer literals, never external/content-derived input.
- **Zip-slip / path traversal**: properly guarded.
  `Aurora.Web/Services/PhaseZeroSessionWorkspaceService.cs` validates each zip
  entry (rejects `.`/`..` segments, re-verifies the resolved path stays under
  the extraction root via `PathContainment.IsPathWithinDirectory`, enforces
  size/count limits) before extraction.
- **Secrets/credentials**: none found in a repo-wide grep.
- **Aurora.Web**: no CORS middleware configured (default same-origin only, HTTPS
  redirection and antiforgery enabled); session workspaces are per-Blazor-circuit
  scoped, not addressable by a guessable ID; upload size/type is validated
  server-side.
- **Deserialization**: no `BinaryFormatter`, no unsafe `XmlSerializer`/JSON
  type-handling found.
- **Update mechanism**: Velopack uses `GithubSource` over HTTPS via the GitHub
  releases API; no custom/HTTP feed URLs found.

One minor hardening suggestion — **XXE consistency**: some XML readers of
third-party content explicitly harden against XXE (`XmlResolver = null`,
`DtdProcessing.Prohibit` — e.g. `TranslatorSpellcastingReader.cs`,
`ContentReviewContracts.cs`, `LocalCorrectionDocument.cs`, `CharacterFileIo.cs`),
while others rely on net10.0's safe-by-default behavior without setting it
explicitly (`AuroraXmlCatalogReader.cs`, `DataManager.cs`,
`ImportedCharacterSummary.cs`, `ContentIndexUpdateService.cs`,
`BaselineContentCatalogService.cs`, `PhaseZeroSessionWorkspaceService.cs`). Not
currently exploitable given framework defaults, but worth standardizing given
content packs originate from arbitrary third parties — defense-in-depth against
a future framework or configuration change.

   `remaining-conflict-table.md`; need author/source review before a release
   that touches package resolution.

   `pre-ui-validation-2026-09-15.md`; flagged as needing a dedicated UI
   switching-test repro, not yet root-caused.
4. **Android/mobile memory profiling** for the v12 content loader remains open
   (desktop peak fixed 844→617 MiB this month; mobile unverified).
