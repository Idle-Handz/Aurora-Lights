# Solution audit, October 2, 2026

Full-solution pass for latent bugs and optimization headroom, with an emphasis on load time. Run
against the working tree at `028ebcb` plus the uncommitted character-load work. Measurements come
from the shipped content database (`buildtmp/corpus-review-20260929-203251/case`, 20,946 prepared
elements, data version 17), the September 29 corpus run logs, the harness's own `profile-load` and
`profile-projection` modes, and three standalone benchmarks built against the production assemblies.
No production code was changed for any measurement.

## Summary

Startup content load is **22.4 s** and retains **544 MiB**. Three quarters of both is work the app
does not need yet: post-processing synthesizes **80,228 elements on top of the 21,194** the database
supplies, and 79,032 of those are a spell-by-spellcasting-list cross product that exists only to
populate one picker.

Character load is 20–50 s per character. Two causes, both measured or read directly from source: the
expression evaluator re-parses and re-compiles every expression on every evaluation (**410 µs per
call, 140× improvable**), and `ProgressionManager.ProcessElement` recurses into each element's
children **twice**, making node visits exponential in graph depth (median depth 6 → 64 visits per
leaf per pass).

Correctness is in better shape than performance. The empty-catch sweep has held (zero remain), every
Blazor component that subscribes to an event disposes it, and no caller mutates the cached element
graph. The defects found are smaller and listed below.

cheapest first move, because everything below is otherwise invisible.

#### The 79,032-element cross product

`InternalElementsGenerator.GenerateInternalSpells` emits one "Additional Spell" proxy `Item` per
(spell × spellcasting list). The catalog has 2,136 spells and 36 distinct non-extension spellcasting
list names, plus one empty entry: **2,136 × 37 = 79,032 proxies**, which is essentially all 80,228
synthesized elements. The other generators are rounding error by comparison — 539 feats, 289
proficiencies, 147 ASIs, 91 languages, 2,136 spell scrolls, and 48 classes × 18 ASI/Feat class
features.

Their only consumer is the **Add Custom Feature** picker, via
`EquipmentService.GetCustomFeatureCategories` / `SearchCustomFeatures`, which match on a name
beginning `"Additional "`. They are excluded from the compendium (`IncludeInCompendium = false`).
So the app spends roughly 11 s and 400 MiB at every launch building a cross product for a dialog the
user may never open.

**Recommended:** generate lazily, per category, on first use of that picker. Opening "Additional
Wizard Spell" needs 2,136 proxies, not 79,032.

One real constraint: saved characters reference these ids in `<custom-features>`, and
`BuildService.ReapplyCustomFeatures` resolves them by id at load. Lazy generation therefore needs a
single-id path — synthesize the one proxy an id names — rather than only a category path. Note also
that precomputing them into the content database is *not* the answer: reading 79,032 more elements
would cost more than generating them (`ParseElement` measured at 174 µs per element).

A second consequence: `CompendiumService.BuildCatalogAsync` walks `ElementsCollection`, so every
compendium build iterates 101,422 elements instead of 21,194 — a 5× cost on a user-facing operation
that filters almost all of it away.

#### What is not the problem

I expected `XmlDocument.LoadXml` per element to dominate and it does not. Parsing the entire catalog
costs 1.11 s; a single concatenated document is only 1.2× faster and parallelizing is no faster at
all. `ElementBaseCollection` being an `ObservableCollection` is likewise irrelevant (1.1 ms for
20,946 adds), and the linear parser scan is 6.5 ms. None of these is worth touching.

### Character load: the expression evaluator

`ExpressionInterpreter` calls `_interpreter.Eval<bool>(expressionString)` on every evaluation.
DynamicExpresso parses and compiles the string each time; there is no cache. On top of that, each
call re-runs uncompiled `Regex.Matches` and a series of `string.Replace` rewrites.

Benchmarked against the shipped `lib/DynamicExpresso.Core.dll` with the engine's real expression
shapes:

| shape | per call |
|---|---|
| `Eval()` — what the engine does today | **410.3 µs** |
| parse once to a `Lambda`, `ids` as a parameter, invoke | 4.3 µs (**96×**) |
| parse once to a compiled delegate, invoke | 2.9 µs (**140×**) |

At 50,000 evaluations per character load that is 20.5 s today against 0.15 s cached, which matches
the 20–50 s of unlogged compute visible between trace lines during the corpus run.

The fix is a cache keyed on the converted expression string. It must bind `ids` as a `Parameter`
rather than via `SetVariable`, because DynamicExpresso resolves variables at parse time and a cached
lambda would otherwise capture a stale collection. Nine call sites across `ProgressionManager`,
`StatisticsHandler2`, `BuildSelectionOptionResolver` and the selection services funnel into these
four methods, so the change is contained — but it is engine behaviour, so it needs the legacy gates
and a corpus re-run behind it.

I measured the per-call cost, not the per-load call count; the count above is inferred from the
observed gaps and the structure below.

### Character load: the double recursion

`ProgressionManager.ProcessElement` recurses into `element.RuleElements` **twice** — once before
processing the element's own selection and grant rules, once after:

```csharp
foreach (var ruleElement in element.RuleElements) this.ProcessElement(ruleElement, currentLevel);
this.ProcessSelectionRules(element, currentLevel);
this.ProcessGrantRules(element, currentLevel);
if (element.HasSpellcastingInformation && ...) { ... }
foreach (var ruleElement in element.RuleElements) this.ProcessElement(ruleElement, currentLevel);
```

Node visits are therefore `2^depth` per root pass. Saved choice-tree nesting across the sixty-character
corpus has a median depth of 6 and a maximum of 9:

| depth | visits per leaf, per pass | characters |
|---:|---:|---|
| 6 | 64 | median |
| 9 | 512 | Remy Morningstar, Remy Morningstar (Strahd) |

The second pass presumably exists so that children added by `ProcessGrantRules` get processed. If so,
the *first* loop is the redundant one for newly granted children and the doubling is accidental. This
is decompiled legacy code, so Legacy carried it too — which is an argument for fixing it carefully,
not for leaving it.

### Character load: redundant full-graph passes

`CharacterManager.RegisterElement` calls `ProcessExistingElements` **eight times** per registration.
Every `switch` branch does `Process(element)` followed by `progressionManager.ProcessExistingElements()`,
and then after the switch it unconditionally runs `_progressionManager.ProcessExistingElements()` plus
one for every class progression manager. Nothing mutates state between the per-branch call and the
trailing block, so the per-branch call is redundant in all six branches — roughly a **2× multiplier
on the dominant cost**, removable.

`UnregisterElement`, by contrast, calls it zero times.

Ordering changes slightly if the per-branch call is dropped (main-then-class-managers instead of
class-manager-first), and "these passes are convergent" is exactly the assumption that the firearm
oscillation bug violated. Confirm against the corpus rather than by inspection.

### Smaller load-time items

- **`ElementBaseCollection.GetElement(id)` is a linear `FirstOrDefault`** over the whole catalog —
  now 101,422 elements. It is called from 34 places including per saved element during character
  load, and `ElementIdAliases.Resolve` calls it up to twice per id. A dictionary index on the
  collection would remove roughly 20 M string comparisons per character load.
- **`ElementExtensions.Copy<T>()` is a fully reflective recursive deep clone** — `MemberwiseClone`
  through `MethodInfo.Invoke`, `GetFields` per type per object with no `FieldInfo` caching, and
  unbounded recursion into every non-primitive field. Measured: **11.3 µs** for a `StatisticRule`,
  **171 µs** for an `ElementBase` with its `ElementNode` attached. `ProgressionManager.GetStatisticRules`
  calls `x.Copy<StatisticRule>()` on *every* rule on *every* statistics pass, and
  `SetCharacterDetails` runs one pass per element registration — 500 rules × 400 passes is 2.3 s of
  pure cloning. A hand-written copy constructor for `StatisticRule` is a contained fix.
- **`XmlContentFallbackService.PrepareProjection` runs eagerly on every successful load** and retains
  11.2 MiB, to be ready in case a *later* load fails (`profile-projection`: 3.84 s for the mode).
  Making it lazy costs nothing on the success path.
- **`InitializeItemDetails`** resolves each weapon's and armour's support tags with a linear catalog
  scan — 187 items × ~6 supports × 101,422 elements. Measured as roughly 0.2 s, so it is real but
  not urgent; a lookup built once would remove it.

## Correctness

### Clean

- **Zero empty catch blocks** across `Aurora.App`, `Aurora.Logic` and `Aurora.Components`. The
  September 17 sweep has held.
- **Every Blazor component that subscribes to an event implements `IDisposable`** — twelve components
  checked, no leaked subscriptions.
- **No caller mutates the cached element graph.** `GetElements()` returns `_elementsCache` by
  reference where it used to return a fresh collection, which would corrupt the cache; the two
  callers that hold the result only read it, and `WithoutRuleParent` copies before removing.
- **`DbElementLoader`'s `AsyncLocal<LookupState>` is used correctly.** The value flows into the
  `Task.Run` at line 275, and line 697 mutates the pointed-at object rather than the slot, so the
  write is visible to the caller that reads it back at line 303.

### Findings

1. **`async void` in seven places** (`QuickBarDiceCommand.Execute`, `SelectionRuleCollectionService.EvaluateChanges`,
   `SelectionRuleNavigationService.Eval`, three in `AbilitiesContentViewModel`,
   `SelectionRuleComboBoxViewModel.SetSelectionAndRegister`). An exception in any of them terminates
   the process rather than surfacing. None is reachable from `Aurora.App`, `Aurora.Components` or
   `Aurora.Web` — they are all WPF-only — so this is an `Aurora.Lights` risk, not a MAUI one.

2. **`ClassProgressionManager.cs:117` blocks a thread on async work**:
   `Task.Run(() => result = GenerateRandomHitPointsArray(...).Result).Wait()`. The `Task.Run` wrapper
   avoids the classic deadlock, but it still blocks the caller for the duration.

3. **`SearchItemsForSlot` scans the whole catalog per keystroke** — `ElementsCollection.Where(...)`
   with a slot-compatibility test and a source-restriction check per element, over 101,422 elements,
   with no index and no debounce visible at the call site in `GearSlotPickerDialog.razor:177`.
   `ItemPickerDialog` uses the precomputed search index instead; these two pickers should agree.

4. **The custom-feature picker applies no source restriction.** `GetCustomFeatureCategories` and
   `SearchCustomFeatures` do not take a `BuildSourceRestrictionSnapshot`, unlike the inventory paths
   at `EquipmentService.cs:47`, `:108` and `:287`. Content from switched-off books is offered. This
   predates the companion work but companions inherit it.

5. **A root element's own `requirements` are never evaluated.** `ProcessElement` checks
   `HasRequirements` only on granted children (`ProgressionManager.cs:333`) and on grant rules
   (`:316`). Anything registered directly as a root keeps its place regardless. The practical effect,
   new since companions became addable as Extras: a Drakewarden drake or a Steel Defender can be
   attached to a wizard with no archetype. This is pre-existing engine behaviour, but companions are
   the first content where requirements are the only thing tying an element to a class.

6. **The Companions category offers 465 bestiary stat blocks.** Every effective `CompanionElement`
   qualifies, so the list runs from "Aboleth" through the whole dragon age ladder before reaching
   anything a player would call a companion. A usability problem rather than a correctness one.

7. **90 culture-sensitive parse and case operations** in `Builder.Data` and `Aurora.Logic`
   (`Convert.ToBoolean`, `int.Parse`, `ToLower()` with no `CultureInfo`/`StringComparison`). Mostly
   on content values that are ASCII in practice; the risk is a Turkish-locale `ToLower()` on an id or
   a comma-decimal locale on a numeric setter. Worth a sweep, low expected yield.

## Suggested order

1. **Instrument the loader's stages.** Everything above is currently invisible at runtime.
2. **Make the spell proxy cross product lazy.** Largest single win: roughly 11 s and 400 MiB off
   every launch, no engine semantics involved. Needs a single-id path for `<custom-features>`.
3. **Cache parsed expressions.** 140× on the dominant character-load cost. Engine behaviour — legacy
   gates and a corpus re-run.
4. **Drop the redundant `ProcessExistingElements` per branch.** ~2×, same gating.
5. **Fix the double recursion in `ProcessElement`.** Largest structural win on character load, and
   the one most likely to change behaviour; do it last and with the oracle.
6. Index `GetElement`, hand-write `StatisticRule`'s copy, make the fallback projection lazy.
7. The correctness findings, which are all small and independent.

## Implementation: lazy spell proxies (October 2)

The cross product is now built per category on first use. `InternalElementsGenerator` gained
`GetSpellcastingListNames` and an optional list filter on `GenerateInternalSpells`, and
`SpellProxyCatalog` holds the deferred state. `SpellProxyCatalog.Enabled = false` restores the old
behaviour, and the rehearsal harness exposes it as `REHEARSAL_EAGER_SPELL_PROXIES=1` so the two can
be compared on demand.

Measured with `profile-load`, median of three runs each, same database, same session:

| | elapsed | managed | peak working set | elements |
|---|---:|---:|---:|---:|
| eager (previous) | 39.22 s | 552.5 MiB | 657 MiB | 101,422 |
| lazy (now) | **24.46 s** | **329.5 MiB** | **508 MiB** | 24,850 |
| delta | **−14.76 s (−38%)** | **−223 MiB** | −150 MiB | −76,572 |

The absolute figures are higher than the 22.39 s recorded earlier in this document because that was
a single run on a quieter machine; the A/B above was taken back to back and is the comparison to
trust. The saving is larger than the ~11 s the audit predicted.

Four things the change had to preserve, each covered by a test that fails without it:

- **Categories are listed before they are built.** `EquipmentService.GetCustomFeatureCategories`
  unions `SpellProxyCatalog.Categories`, derived from the spellcasting list names alone.
- **A saved character that names a proxy directly still resolves it.** One corpus character (Crow)
  carries `Additional Spell, Acid Splash` as an item in its build tree. `ElementIdAliases.Resolve`
  builds the category on a miss, but only for an id shaped like a proxy.
- **Only the primed catalog grows.** A projection or a test passing its own collection is never
  quietly given generated content.
- **Deliberately unavailable identities stay gone.** Eager generation was followed by a sweep in
  `DbElementLoader` that removed them; the loader now passes that set to `Prime` so a late build
  honours the same exclusion.

Priming happens where the live collection is known: `DbElementLoader` after it copies the
post-processed candidate into the target, and `RunPostProcessing` itself only when it is running over
`DataManager.ElementsCollection` (the XML fallback path). Post-processing a candidate never primes,
because the candidate is discarded.

**Aurora.Tests: 795/795.** Corpus verification of the sixty characters is the remaining gate.

### Corpus verification, and the regression it caught

First corpus run against the lazy build came back **48 clean / 12 flagged** — Crow had regressed. Its
saved build tree names `ID_PHB_INTERNAL_ITEM__SPELL_PROXY_SPELL_ACID_SPLASH` as an item, and the
loader's saved-item path at `CharacterFile.cs:650` resolved it with a plain `GetElement`, not the
alias resolver the hook had been added to. First load reported the proxy and its granted spell as
lost; the roundtrip file was then written without them, so the second load had nothing to miss and
`stateStable` was false.

The unit tests had passed because they exercised `ElementIdAliases.Resolve`, which was only one of
the loader's two lookup paths. Fixed by giving the deferral a single funnel,
`SpellProxyCatalog.ResolveOrBuild`, now used by `Resolve`, the saved-item path and
`BuildService`'s custom-feature lookup, with a test that covers the funnel directly rather than
through one caller.

Re-run: `buildtmp/corpus-lazyproxy-fix-20261002-063446`, **49 clean / 11 flagged**, the same 49 and the same 11 as the baseline, Crow back in
the clean set. 0 errors, 0 input hashes changed, 0 missing grants, and every flagged character
reporting an identical missing set on both loads.

Shard times were roughly twice the September 29 run, which is machine drift rather than the change:
eager `profile-load` measures 39 s on this machine against 22 s in the earlier session, and a single
character measured head to head, two runs each interleaved, came out **eager 150.4 s and 171.9 s
against lazy 146.0 s and 171.2 s** - indistinguishable, with the two eager runs differing from each
other by more than either differs from its lazy counterpart. Peak working set was the clean signal:
**686-694 MiB eager against 539-542 MiB lazy**. Character load is unaffected either way, which is
expected - the saving is at content load, once per process.

**Aurora.Tests: 796/796.**
