Verified during the website policy review:
- Only drive.file is requested: app-created or explicitly authorized files, not general access to the user's whole Drive.
- Drive account permissionId, emailAddress and displayName identify/bind the account. File metadata supports opening, saving and conflict checks.
- Character XML and session data, including HP, spell slots and resources, travel directly between device and Google Drive. This feature has no Idle Handz save-storage backend.
- The device keeps local working copies, session sidecars and recovery copies. Recovery copies are not automatically pruned. Cloud saves are explicit; this is not continuous background synchronization or a guaranteed backup/recovery service.
- Desktop uses system-browser authorization with PKCE/loopback and stores refresh tokens using MAUI SecureStorage. Android uses Google Play services authorization and stores its account binding through SecureStorage. Bundled desktop client configuration identifies the app; it is not a user's account credential.
- Disconnect removes credentials/account binding for that installation. It does not delete Drive/local/recovery files, revoke other devices or globally revoke Google's permission. Users separately manage Google connections and delete their files/copies.
- Reflections can also contact update/content sources and keep local diagnostics. Do not extend the Drive-specific statements into a claim that the entire suite has no network activity, analytics or sharing.
- Desktop authorization is implemented for macOS; platform verification remains separate. Existing docs record an October 8 Windows/Android live roundtrip on version 0.9.4, which does not validate the future disclosure/configuration changes or all conflict/revocation/recovery cases.
